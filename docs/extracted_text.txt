SECTION 1 — PRODUCT VISION & PROBLEM DEFINITION
1.1  What BOT Is
BOT is a schema-aware analytical chatbot that accepts any Excel workbook as its data source and answers natural language questions about that data. It does not hardcode any domain. It infers the schema, relationships, and business meaning from whatever Excel file is loaded.
BOT converts user questions into validated SQL, executes the SQL against an in-memory analytical engine, and returns a direct answer with a full explanation of how that answer was derived.
1.2  One-Line Product Definition
"A domain-agnostic, schema-aware analytics chatbot that converts natural language into validated SQL over any Excel workbook, with multi-table join support, derived metric computation, and automatic query repair."
1.3  The Core Problem
Organizations frequently store operational data across multiple sheets in Excel. These datasets contain implicit relationships: one sheet might store orders, another stores products, and another stores customers. To answer a question like 'Which product had the highest revenue last week?', data must be joined across multiple sheets and a derived metric (revenue = quantity × price) must be computed.
No generic chatbot or simple RAG system can do this reliably. BOT is purpose-built for this exact problem.
1.4  What BOT Must Do
Accept any Excel workbook with one or more sheets
Treat each sheet as a relational database table
Automatically infer schema, column types, and relationships
Build a business glossary of domain-specific terms from the data
Convert natural language questions into structured analytical plans
Compile those plans into valid, safe SQL
Execute SQL against a local DuckDB analytical engine
Format results into human-readable, non-technical answers
Show the SQL used, tables joined, and formulas applied
Automatically repair failed SQL queries and retry once
1.5  What BOT Must NOT Do in MVP
Perform full RAG over raw row content
Use vector databases for table rows
Execute arbitrary LLM-generated Python code
Support multiple simultaneous users or enterprise auth
Persist sessions beyond in-memory storage
Build a full autonomous agent with tools and memory
Require the user to know SQL or the schema

4.3  LLM Strategy
BOT uses the OpenAI API with structured output mode. The primary model is gpt-4o for planning and gpt-3.5-turbo for repair (cheaper, faster for smaller task).
If a local LLM is preferred, use Ollama with llama3 or mistral. The API call pattern is identical — just change the base URL and model name in configuration.
 
  # OpenAI (default)
  LLM_PROVIDER=openai
  LLM_MODEL=gpt-4o
  OPENAI_API_KEY=sk-...
 
  # Local (Ollama fallback)
  LLM_PROVIDER=ollama
  LLM_BASE_URL=http://localhost:11434/v1
  LLM_MODEL=llama3
 
4.4  DuckDB — Why It Wins
Runs fully in-process — no database server to install or maintain
Handles complex JOINs across multiple DataFrames natively
Supports all standard SQL aggregation functions
Supports window functions (LAG, LEAD, RANK, PARTITION BY)
Supports date arithmetic and interval operations
Extremely fast on datasets up to 10M+ rows
Can register Pandas DataFrames as tables directly — no ETL needed
Supports CTEs for readable, maintainable query structure

Function: infer_and_cast_types()
 
  def infer_and_cast_types(df: pd.DataFrame) -> pd.DataFrame:
      '''
      For each column, attempts type coercion in this priority order:
        1. If name contains 'date', 'time', 'at', 'on' -> parse as datetime
        2. If values are numeric strings -> cast to int or float
        3. If values are 'true'/'false', 'yes'/'no' -> cast to bool
        4. If values are integers that look like IDs -> keep as int
        5. Default -> varchar (string)
      Returns the DataFrame with corrected dtypes.
      '''
 
7.3  Module: app/data/duckdb_manager.py
 
  class DuckDBManager:
      '''Singleton connection manager for DuckDB.'''
 
      _instance: Optional['DuckDBManager'] = None
      _conn: Optional[duckdb.DuckDBPyConnection] = None
 
      @classmethod
      def get_connection(cls) -> duckdb.DuckDBPyConnection:
          if cls._conn is None:
              cls._conn = duckdb.connect(settings.DUCKDB_PATH)
          return cls._conn
 
      @classmethod
      def register_dataframe(cls, table_name: str, df: pd.DataFrame) -> None:
          conn = cls.get_connection()
          conn.register(table_name, df)
 
      @classmethod
      def execute(cls, sql: str) -> pd.DataFrame:
          conn = cls.get_connection()
          return conn.execute(sql).df()
 
      @classmethod
      def get_registered_tables(cls) -> list[str]:
          conn = cls.get_connection()
          result = conn.execute('SHOW TABLES').df()
          return result['name'].tolist()
 
      @classmethod
      def reset(cls) -> None:
          if cls._conn:
              cls._conn.close()
          cls._conn = None

8.3  Module: app/data/relationship_detector.py
Function: detect_relationships()
 
  def detect_relationships(registry: SchemaRegistry) -> list[RelationshipMetadata]:
      '''
      Heuristic-based FK detection. Checks:
        1. Column name match: if table A has col 'product_id' and
           table B has col 'product_id' or 'id', infer FK relationship.
        2. Pattern matching: columns ending in '_id' are FK candidates.
        3. Cardinality check: if col A values are subset of col B values,
           A is likely FK pointing to B.
        4. Name overlap: if table name appears in another table's column,
           e.g., 'order_id' in line_items pointing to 'orders' table.
      Returns list of RelationshipMetadata sorted by confidence desc.
      '''

  def build_schema_context_for_llm(registry: SchemaRegistry) -> str:

      Generates a compact but complete schema summary for the LLM prompt.
      Format:

          - customer_id [integer, foreign_key -> customers.id]
          - created_at [timestamp, date_col] range: 2023-01-01 to 2024-12-31
          - total_amount [float, measure] range: 5.00 to 2,450.00
        RELATIONSHIPS:
          orders.customer_id -> customers.id (confidence: 0.98)

SECTION 9 — BUSINESS GLOSSARY LAYER
9.1  Why the Glossary Matters
Users speak in business language. They say 'revenue', not 'SUM(quantity * unit_price)'. They say 'drop', not 'WHERE current_period < previous_period'. The glossary bridges this gap. It stores the SQL expression equivalent of every business term.
9.2  Module: app/data/glossary.py
Pydantic Model: GlossaryTerm
 
  class GlossaryTerm(BaseModel):
      term: str                     # 'revenue'
      aliases: list[str]            # ['sales', 'income', 'total sales']
      sql_expression: str           # 'SUM(quantity * unit_price)'
      description: str             # plain English explanation
      required_columns: list[str]  # columns needed to compute this
      required_tables: list[str]   # tables needed to compute this
      is_comparison: bool          # True if term implies delta (e.g., 'drop')

SECTION 10 — QUERY PLANNING LAYER
10.1  Why a Planner Exists
The LLM does NOT directly write SQL. The LLM first writes a structured JSON plan describing the intent. The SQL Compiler then converts the plan into SQL deterministically. This two-step approach is safer, more debuggable, and more reliable than asking the LLM to produce SQL in one shot.

10.3  The QueryPlan JSON Schema
This is the complete structure the LLM must return. Every field is validated by Pydantic before SQL compilation begins.
 
  class JoinSpec(BaseModel):
      left_table: str
      left_column: str
      right_table: str
      right_column: str
      join_type: str = 'INNER'   # INNER, LEFT, RIGHT
 
  class FilterSpec(BaseModel):
      table: str
      column: str
      operator: str  # '=', '>', '<', '>=', '<=', 'BETWEEN', 'IN', 'LIKE'
      value: Any     # literal or date expression like 'yesterday'
      is_date_filter: bool = False
 
  class MetricSpec(BaseModel):
      name: str            # alias to use in SELECT
      expression: str      # SQL expression e.g. 'SUM(quantity * price)'
      is_derived: bool     # True if not directly in a column
 
  class QueryPlan(BaseModel):
      intent: str                         # e.g. 'compare_revenue_over_time'
      tables_needed: list[str]            # exact normalized table names
      joins: list[JoinSpec]               # ordered list of joins
      filters: list[FilterSpec]           # WHERE clause conditions
      metrics: list[MetricSpec]           # SELECT expressions
      group_by: list[str]                 # GROUP BY columns (table.column format)
      order_by: list[str]                 # ORDER BY columns
      limit: Optional[int]                # LIMIT N
      requires_comparison: bool           # True if time window comparison needed
      comparison_periods: Optional[dict]  # {'current': 'yesterday', 'previous': 'day_before'}
      output_columns: list[str]           # final column names in result
      plain_english_plan: str             # LLM explanation of its own plan

SECTION 11 — SQL COMPILATION LAYER
11.1  Module: app/core/compiler.py
The compiler takes a validated QueryPlan and deterministically produces a SQL string. This layer has no LLM involvement. It is pure Python logic.
Function: compile_plan_to_sql()
 
  def compile_plan_to_sql(plan: QueryPlan) -> str:
      '''
      Main compilation function.
      Dispatches to the correct builder based on plan.requires_comparison.
      Returns a complete, executable SQL string.
      '''
      if plan.requires_comparison:
          return _compile_comparison_query(plan)
      return _compile_standard_query(plan)
 
Function: _compile_standard_query()
 
  def _compile_standard_query(plan: QueryPlan) -> str:
      '''
      Builds SQL for non-comparison queries.
      Structure:
        WITH <cte_name> AS (
          SELECT <metrics>
          FROM <primary_table>
          <JOIN clauses>
          WHERE <filters>
          GROUP BY <group_by>
          ORDER BY <order_by>
          LIMIT <limit>
        )
        SELECT * FROM <cte_name>
      '''
 
Function: _compile_comparison_query()
 
  def _compile_comparison_query(plan: QueryPlan) -> str:
      '''
      Builds SQL for time comparison queries using CTEs.
      Structure:
        WITH
          current_period AS (
            SELECT ... WHERE date_col = 'yesterday'
          ),
          previous_period AS (
            SELECT ... WHERE date_col = 'day_before'
          )
        SELECT
          c.group_col,
          c.metric AS current_value,
          p.metric AS previous_value,
          c.metric - p.metric AS delta,
          ROUND((c.metric - p.metric) / NULLIF(p.metric, 0) * 100, 2) AS pct_change
        FROM current_period c
        LEFT JOIN previous_period p USING (group_col)
      '''
 
Function: resolve_date_expression()
 
  def resolve_date_expression(expr: str, date_col: str) -> str:
      '''
      Converts natural date expressions to DuckDB SQL.
      'yesterday'             -> CURRENT_DATE - INTERVAL '1 day'
      'today'                 -> CURRENT_DATE
      'last 7 days'           -> CURRENT_DATE - INTERVAL '7 days'
      'this week'             -> DATE_TRUNC('week', CURRENT_DATE)
      'last month'            -> DATE_TRUNC('month', CURRENT_DATE - INTERVAL '1 month')
      'last_2_days'           -> BETWEEN CURRENT_DATE-2 AND CURRENT_DATE
      'day_before_yesterday'  -> CURRENT_DATE - INTERVAL '2 days'
      '''
 
Function: build_join_clause()
 
  def build_join_clause(joins: list[JoinSpec]) -> str:
      '''
      Takes list of JoinSpec objects.
      Returns JOIN SQL string.
      Example output:
        INNER JOIN order_line_items ON orders.order_id = order_line_items.order_id
        INNER JOIN products ON order_line_items.product_id = products.product_id
      '''
 
Function: build_where_clause()
 
  def build_where_clause(filters: list[FilterSpec]) -> str:
      '''
      Converts list of FilterSpec to SQL WHERE clause.
      Handles: =, >, <, >=, <=, BETWEEN, IN, LIKE, IS NULL, IS NOT NULL.
      Date filters routed through resolve_date_expression().
      Returns 'WHERE ...' string or '' if no filters.
      '''

DuckDB-Specific SQL Patterns
BOT leverages these DuckDB-specific features:
 
  -- Date arithmetic
  WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
 
  -- Date truncation
  SELECT DATE_TRUNC('week', created_at) AS week_start
 
  -- Safe division (no divide-by-zero error)
  SELECT revenue / NULLIF(order_count, 0) AS aov
 
  -- Window function for ranking
  SELECT product_name, revenue,
         RANK() OVER (ORDER BY revenue DESC) AS revenue_rank
 
  -- LAG for period comparison
  SELECT date, revenue,
         LAG(revenue) OVER (ORDER BY date) AS prev_revenue

  def render_answer(response: dict):

      st.write(response['answer']['summary'])
 
      # Result table
      if response['answer']['result_table']:

      # Expandable sections
      col1, col2, col3 = st.columns(3)
 
      with col1.expander('SQL Query Used'):
          st.code(response['answer']['sql_used'], language='sql')
 
      with col2.expander('How This Was Answered'):
          exp = response.get('explanation', {})
          st.write('**Tables joined:**')
          for j in exp.get('joins_performed', []):
              st.write(f'• {j}')
          st.write('**Formulas computed:**')
          for f in exp.get('formulas_computed', []):
              st.write(f'• {f}')
 
      with col3.expander('Query Metadata'):
          st.metric('Rows returned', response['answer']['row_count'])
          st.metric('Response time', f'{response["latency_ms"]:.0f} ms')
          if response['answer']['was_repaired']:
              st.warning('Query was auto-repaired')
 
SECTION 21 — SESSION & STATE MANAGEMENT
21.1  In-Memory Session Store
For MVP, sessions are stored in memory using a Python dictionary keyed by session_id. Sessions are not persisted to disk. They reset when the server restarts.
 
  class SessionStore:
      _sessions: dict[str, SessionState] = {}
 
      @classmethod
      def get_or_create(cls, session_id: str) -> SessionState:
          if session_id not in cls._sessions:
              cls._sessions[session_id] = SessionState(
                  session_id=session_id,
                  created_at=datetime.utcnow(),
                  last_active=datetime.utcnow()
              )
          return cls._sessions[session_id]
 
      @classmethod
      def save_turn(cls, session_id: str, turn: ChatTurn) -> None:
          session = cls.get_or_create(session_id)
          session.turns.append(turn)
          session.last_active = datetime.utcnow()
          # Keep only last 50 turns in memory
          session.turns = session.turns[-50:]
 
      @classmethod
      def get_history(cls, session_id: str, limit: int = 20) -> list[ChatTurn]:
          session = cls.get_or_create(session_id)
          return session.turns[-limit:]
 
      @classmethod
      def clear(cls, session_id: str) -> None:
          cls._sessions.pop(session_id, None)

sqlglot AST parsing catches obfuscated destructive statements
Table names validated against schema registry — no SQL injection via table names

LIMIT automatically applied if missing — prevents runaway memory usage
Query timeout enforced at DuckDB level

File saved to isolated data/ directory, not served publicly
Sheet names sanitized before DuckDB table registration

LLM output parsed as structured JSON only — no raw text execution
Plan validation runs before SQL compilation — catches hallucinated table names
All table and column names in the plan are verified against the registry
LLM is never given the ability to modify data or call external APIs
